### 10. Frontend: feature-slicing over a flat layout

**Status:** Accepted, 2026-05-27.

The original [code-architecture.md](../code-architecture.md) described an intentionally-minimal frontend: an `app/` of routes, a `components/` for primitives and "domain components," a single `lib/api.ts`, and "state management deliberately absent" with the client layer left undecided. That was the right starting point when the only question was "can a page fetch and render." It stops serving the MVP once the surfaces are real: auth (login/signup with a cookie session), catalog browsing, an optimistic cart, checkout, and account/order history. These are several distinct surfaces that share a set of primitives, and the cart and the session are referenced from many routes. A flat layout has no obvious home for that — feature logic scatters across route folders and shared state has nowhere to live.

**Decision.** Organize the frontend by feature. Each surface owns a folder under `features/<name>/` containing its data access (`api.ts`), its mutations (`actions.ts`), its validation (`schemas.ts`), and its components. `app/` holds only route plumbing (page/layout/loading/error/not-found). `components/` is the single technical-layer folder — the App-Router analogue of the backend's `internal/` — holding feature-agnostic primitives in `components/ui/`. The import direction is `app/` → `features/` → `components/` → `lib/`; **features never import each other**, and anything two features share moves down into `components/ui/` or `lib/`.

The primitive layer is polymorphic: variants via CVA, element substitution via `asChild` (`@radix-ui/react-slot`). Composite primitives (`Field`, `Card`, `Dialog`, `Sheet`, `Tabs`) and feature composites (`ProductCard`, `Cart`) use the **compound + context** pattern — sub-parts attached via `Object.assign(Root, { Sub })`, shared state via React context. A constraint learned in practice: a compound assembled in a `"use client"` module only resolves its sub-components when the *consumer* is also a client component; across the RSC boundary the attached parts come back `undefined`. This is why `ProductGrid` and `CartNavSlot` exist as thin client wrappers.

Reads run in Server Components through each feature's `api.ts`. Mutations are **Server Actions** that call `revalidatePath("/", "layout")` to refresh the affected tree (path revalidation, not tag — Next 16's "default" cache profile silently no-ops `revalidateTag`). The cart wraps `useOptimistic` over its actions. Auth is a gateway-issued cookie; the server fetch helper forwards `Set-Cookie` from auth mutations (`forwardSetCookies()`, because Next.js does not auto-relay it), and `proxy.ts` gates protected routes by **validating** the cookie against the gateway's `/me`, not by checking its presence.

**Alternatives considered:**
- *Keep the minimal `app/` + `components/` layout.* Rejected — with five real surfaces, feature logic scatters across route folders and shared concerns (cart, session) have no home.
- *Co-locate everything in `app/<route>/_components/`.* Rejected — the cart and auth are referenced from many routes, so route-local co-location forces awkward cross-route imports up the tree.
- *Add Redux / Zustand / React Query.* Rejected — RSC for reads, Server Actions for writes, and `useOptimistic` for the one optimistic surface cover every case the MVP has. A client store would be unused weight.

**Consequences.** New features have a predictable home (`features/<name>/`) and primitive variants have one place to live (`components/ui/`). The cookie-forwarding server fetch couples the frontend to the gateway's auth-cookie contract — a deliberate, documented coupling. There is no frontend test coverage; the net is `tsc --noEmit` + `eslint` + `next build`, leaning on generated types from `openapi.yaml` to catch the bugs a thin component test would. Two known limitations: cart quantity-decrease is non-atomic (DELETE + POST) pending a backend `PUT` cart-item endpoint, and money is handled as the gateway's decimal-string `{ amount, currency }` shape with formatting centralized in `lib/money.ts` rather than parsed to a number.
